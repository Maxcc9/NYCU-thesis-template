\chapter{Evaluation}
\label{ch:method}
\label{ch:evaluation}
%=============================================================

% ─── 章節破題 ───────────────────────────────────────────────
本章評估 PaceANN 的兩個機制在並發服務下的效果：先交代實驗設計與量測協定，再逐一呈現各項結果，
檢驗第~\ref{ch:motivation}~章的分析所引出的設計主張——SSD 佇列在高並發下主導延遲、beam search 大量 hop 在收斂後才執行、以及各查詢的收斂熱區隨分布漂移。
由於評估涉及三個在架構上有本質差異的系統，公平性尤為關鍵：所有對照都必須在同等資源限制下進行，
本章以獨立節次（\S\ref{sec:fairness}）專門處理記憶體預算的正規化。

選 100M 這個規模，是因為它夠大、在有限記憶體預算下 SSD 儲存無可避免，正好對應本研究關注的磁碟式情境。

主要實驗以 SPACEV100M 為主結果（i.i.d.）：它取自 Microsoft Bing 搜尋引擎的實際查詢向量，int8 型別與生產環境的檢索向量特徵一致，
且是三者中最常見於社群交叉比對的設定。SIFT100M、DEEP100M 則用於複製驗證，確認主要結果能否推廣到不同型別（uint8／float）與維度的資料集。
查詢集一律使用官方的 10,000 筆 query、以 top-10 精確最近鄰為 ground truth；所有量測都用完整 10,000 筆、不做截斷，以確保 recall 估計的統計穩定。

DiskANN 與 PaceANN 共用同一份 Vamana 索引，以最大出度 $R=96$、建構搜尋列表 $L_\text{build}=120$ 建構；
$R=96$ 是圖密度與 I/O 效率之間的折衷——sector 大小固定，$R$ 越大每次要讀的 sector 越多，$R=128$ 雖連接更豐富但可能拖低效率。
PipeANN 以其原論文建議的 $R=96$、$L_\text{build}=128$ 建構，沿用原設定以維持與其論文比較時的忠實度。
Starling 則採用自己的設計：圖度數 $R=31$（明顯低於前兩者，是其架構本身的選擇）、$L_\text{build}=128$，並額外做 block shuffling 把相鄰節點打包到同一磁碟頁面；
其 navigation graph（mem-index）另以 $R_\text{mem}=20$、$L_\text{mem}=128$ 建構，涵蓋約 0.1\% 的隨機採樣節點。
各系統圖的建構細節不同，是因為三者索引格式互不相容、各自照原論文的推薦設定建構，這是既有評估方法下的標準做法（各系統跑在各自最佳配置），我們在呈現比較時都會標明。

%-------------------------------------------------------------
\section{公平性協定：記憶體預算正規化}
\label{sec:fairness}
%-------------------------------------------------------------

PaceANN 與 Starling 在架構上的根本差異在於：

\begin{itemize}
  \item DiskANN / PaceANN 的最小啟動記憶體僅需 PQ 壓縮向量（SPACEV100M 為 1 億點 $\times$ 32\,bytes/vec $=$ 3.2\,GB），
    剩餘預算可彈性分配給 PAC。
  \item Starling 在啟動時強制載入 \texttt{partition.bin}（827\,MB）到兩個記憶體結構
    （\texttt{id2page\_} 約 400\,MB、\texttt{gp\_layout\_} 約 400\,MB），
    加上 navigation graph（約 31\,MB），
    最小 RSS 固定為 \textbf{3.07\,GB}，無法降低。
\end{itemize}

若直接以 Starling 的最小 RSS（3\,GB）作為統一預算，PaceANN 的快取空間會被壓縮到不合理的下限；
若各系統各自取最優絕對預算，則資源投入不對等，比較失去意義。

因此本研究以固定的總記憶體預算（涵蓋 PQ 與快取）作為基準，各系統用滿此上限但不超過，確保比較的是相同硬體成本下的效能。
預算訂為 PQ 壓縮向量表大小的兩倍（$\text{budget} \approx 2\times\text{PQ}_{\text{floor}}$），
在 SPACEV100M（PQ\_floor $=3.2$\,GB）上為 \textbf{8\,GB}，各系統實測 RSS 落在 7.44–7.96\,GB 之間（見 \S\ref{sec:eval-compare} 的結果）。

量測一律冷啟動、不做暖機：server 全新啟動後直接以原始查詢集完整跑一次，不重複、不循環。
若以重複查詢預熱，PaceANN 的快取命中率會被人為灌高、I/O 趨近於零，量到的就不是真實流量下的效能；
快取僅透過 BFS 冷啟動種子與查詢過程中的 demand-fill 自然累積。

執行緒方面，所有系統都設 $T = 32$ 個 worker thread，beam width 依各系統的最優設定
（DiskANN 與 PaceANN 用 $W = 8$，Starling 用 $W = 4$，與其原論文一致）。

%-------------------------------------------------------------
\section{量測方法論}
\label{sec:measurement}
%-------------------------------------------------------------

本研究所稱的\emph{並發服務}（concurrent serving，亦稱 server mode）並非 DiskANN 內建功能，
而是我們為評估並發服務情境所實作的\textbf{共用測試客戶端}：以並發度 $C$ 控制同時在制的查詢數，
透過 TCP 向各系統的原生 server 發送查詢，並以相同的協定格式與計時方式量測 QPS 與延遲，確保這一層對四個受測系統一致。
但各系統 server 端的並發引擎本身是各自的原生實作，並不強制統一：
DiskANN／Starling／PaceANN 採固定 $T=32$ 個阻塞式 I/O worker thread，可安全超額訂閱到少數核心；
PipeANN 則是 io\_uring SQPOLL 架構，執行緒與實體核心的對應方式不同，因此其公平並發點也不同
（詳見 \S\ref{sec:eval-compare} 的討論）。

延遲數字（平均、P50、P99、P999）都在 server 端計算，時間戳從 worker thread 完整收到查詢封包後開始、到送出結果前結束，
排除 TCP 建連與網路傳輸，讓延遲只反映搜尋演算法本身的成本。QPS 則在 client 端以牆鐘時間計算，從發出第一筆查詢到收到最後一筆回應，反映端到端的吞吐量。

主要結果以並發度 $C \in \{16, 32\}$ 呈現：$C=16$ 是中等並發的典型 server 負載（等於執行緒數的一半，也是 PipeANN 的公平執行點），
$C=32$ 則讓並發度追平執行緒數（$C=T$），使每個 worker 都有查詢在跑、每 hop 各發 $W$ 個讀取，SSD 端的有效佇列深度 $D_\text{eff}=C\times W$ 遠超 knee，排隊行為主導延遲。
其中 $C=16$ 是主要的 QPS 比較點，因為此時四個系統都落在有意義且公平的工作區間。

搜尋長度 $L$ 是控制 recall 的主要旋鈕：$L$ 越大 recall 越高，但每筆查詢的 hop 數與 I/O 也越多。
藉由掃描 $L \in \{20, 30, 50, 80, 100, 150, 200, 250, 300\}$，可在 recall 軸上畫出 QPS--recall 的 Pareto 曲線，涵蓋 recall 約 0.60 到 0.99 的區間；此種以 recall--QPS Pareto 曲線在等召回率下比較不同系統的方法，沿用自 ANN 標準評測實務\cite{aumuller2020annbench}。

%-------------------------------------------------------------
\section{量測指標定義}
\label{sec:metrics}
%-------------------------------------------------------------

\begin{description}
  \item[Recall@10]
    $|S_{10}(q) \cap G_{10}(q)| \;/\; 10$，
    其中 $S_{10}(q)$ 為系統返回的 top-10，$G_{10}(q)$ 為 ground truth top-10。
    以 10,000 筆 query 的算術平均值報告。

  \item[QPS（Queries Per Second）]
    $n_\text{total} / T_\text{wall}$，
    以 client 端牆鐘時間計算，
    包含 TCP 傳輸延遲（通常 $< 0.1\,\text{ms}$，在 localhost 模式下可忽略）。

  \item[Server-side Latency（Mean / P50 / P99 / P999）]
    以 server 端的處理時間計算（不含 TCP 傳輸）。
    P99 與 P999 是評估尾延遲行為的主要指標，
    對應 SLA 中「99\% / 99.9\% 請求須在時限內完成」的要求。

  \item[MeanIOs]
    每次查詢觸發的 SSD 讀取次數的平均值（不含快取命中）。
    四個受測系統皆回報此數字，用於解釋各系統 QPS 差異的來源；
    在 \S\ref{sec:eval-ablation} 的消融實驗中，此指標特別用於量化 CA-ET 的 I/O 節省效果。

  \item[RSS（Resident Set Size）]
    Server process 在量測期間達到的峰值常駐記憶體大小，
    以 \texttt{/proc/\$PID/status} 的 \texttt{VmHWM}（high-water mark）欄位讀取，
    而非當下瞬時值 \texttt{VmRSS}，以避免因記憶體釋放而低估實際峰值用量。
    用於驗證實際記憶體用量是否在預算內。
\end{description}

\section{iso-recall 下的系統比較}
\label{sec:eval-compare}
%-------------------------------------------------------------

第一組實驗在均勻（i.i.d.）查詢下，比較四個系統在相同 8\,GB 記憶體預算下的效能。
各系統各自掃描搜尋長度 $L$，得到召回率對 QPS、平均延遲、尾延遲與 I/O 的完整 Pareto 曲線。
PaceANN 在此採用 OPQ 壓縮（32\,bytes/vector）與 beam width 8 的配置，並同時啟用動態快取與早停。

圖~\ref{fig:pareto-throughput}~至圖~\ref{fig:pareto-io}~分別呈現三個 100M 級資料集（SPACEV100M／SIFT100M／DEEP100M，由左至右）
在 $C=16$ 下的四項指標對 Recall@10 的關係。PaceANN（藍色菱形）在 SPACEV100M 上對 DiskANN、Starling、PipeANN 三者全程領先；
在 DEEP100M 與 SIFT100M 上則穩定領先 DiskANN 與 Starling，但相對 PipeANN 的優勢並不一致——僅在最低召回率（$L=60$）的點上領先，
$L$ 提高後 PipeANN（使用其自身最強的 \texttt{pipe\_search} 機制、於其公平並發點量測）反而反超，且差距隨召回率上升而擴大
（DEEP100M 在 $L=200$ 時 PipeANN QPS 領先 PaceANN 達 24\%）。這代表 PaceANN 相對 DiskANN／Starling 的領先具有一致性，
但相對 PipeANN 則是資料集相依、甚至領先方向會反轉的結果，本論文選擇誠實呈現而非只挑選有利的資料集比較。
Starling 的靜態 block-shuffling 佈局讓它在低召回率時 I/O 效率最好，但曲線斜率較陡，高召回率時反而落後於 PaceANN 與 DiskANN。

PipeANN 的公平並發點為 $C=16$（見下段討論），以上四張圖即在該並發點下量測，並使用其論文的headline機制 \texttt{pipe\_search}（$\text{mode}=2$，io\_uring 管線化 I/O 與運算重疊搜尋）而非其自身消融用的 \texttt{beam\_search}（$\text{mode}=0$）。
Starling 的 navigation graph seed 深度採用其驗證過的設定 $L_\text{mem}=100$。

在高並發下，我們另外比較各系統的 QPS 與尾延遲。PipeANN 的 \texttt{pipe\_search} 用 io\_uring 的 SQPOLL 與非阻塞完成輪詢
（busy-spin，持續呼叫 \texttt{io\_uring\_peek\_batch\_cqe} 而非阻塞等待），這代表每個搜尋執行緒與其對應的 SQPOLL kernel thread
各自需要獨佔一顆實體核心空轉，跟 DiskANN／Starling／PaceANN 的阻塞式 I/O（可安全超額訂閱到多個執行緒共用少數核心）本質不同。
在實驗機的 32 執行緒上，其公平執行點為 $C=16$（16 個搜尋執行緒加 16 個 SQPOLL 執行緒恰好用滿 32 核，無超額訂閱）；
一旦 client 端並發推到 $C=32$，等同讓這套 busy-spin 機制在同一批核心上 2 倍超額訂閱，觸發其設計上未涵蓋的病態尾延遲，
而非單純的吞吐量飽和。故 PipeANN 的主要比較數字以其公平點 $C=16$ 呈現，其餘系統則跑到 $C=32$（見 \S\ref{sec:eval-discuss} 的公平性討論）。
以 $\approx 0.98$ recall（$L=200$）為例：$C=32$ 下 DiskANN QPS $2939.2$（P99 $13.49$\,ms）、
Starling QPS $3257.6$（P99 $15.84$\,ms）、PaceANN QPS $4820.9$（P99 $12.36$\,ms）；
PipeANN 在其公平點 $C=16$ 為 QPS $2695.4$（P99 $8.12$\,ms）。
若仍將 PipeANN 推到 $C=32$，QPS 幾乎不再成長（實測 $2713.9$，僅 $+0.7\%$），代表其架構在 $C=16$ 已達其吞吐上限，
超額訂閱後多餘的並發請求無法轉換為更多吞吐量。尾延遲方面，$L=160$ 時 P99 從 $C=16$ 的 $7.29$\,ms 上升到 $C=32$ 的 $12.46$\,ms（$1.71\times$），
略高於其餘三個阻塞式 I/O 系統同區間的漲幅（DiskANN $1.40\times$、PaceANN $1.38\times$、Starling $1.56\times$），
但並非早期以 \texttt{pipeline\_width}$=4$ 量測時觀察到的數倍暴衝——校準為官方建議的 \texttt{pipeline\_width}$=32$ 後，
這個相對更高的漲幅仍與其 SQPOLL 執行緒在超額訂閱下需與其他執行緒競爭實體核心的架構解釋一致，只是幅度較為溫和。

其中 \texttt{full} 對 \texttt{cache\_only} 的差距，是在相同 OPQ、beam width 與快取預算下\emph{只切換早停開關}所得，
因此可視為早停這一機制的乾淨貢獻：實測 QPS 提升 $C=16$ 時 $+45.1\%$、$C=32$ 時 $+46.3\%$，隨並發度上升而略微放大，
支持「早停省下的 I/O 在高並發時把頻寬讓回給佇列、進而放大吞吐量」的論點。
四組比較的完整圖像是：\texttt{cache\_only} 相對 baseline 有 $+9.6\%$（$C=16$）到 $+12.2\%$（$C=32$）的溫和提升，
單靠動態快取重疊收斂熱區的效果有限；\texttt{ET\_only} 相對 baseline 則有 $+48.9\%$（$C=16$）到 $+50.8\%$（$C=32$）的大幅提升，
顯示消除收斂後冗餘 hop 是本實驗設定下更主要的增益來源；而 \texttt{full} 對 \texttt{ET\_only} 僅再貢獻 $+6.8\%$（$C=16$）到 $+8.8\%$（$C=32$），
代表快取對早停可靠性的「使能效應」存在但幅度不大——與平均 I/O 的變化趨勢一致（210.26 $\to$ 177.08 $\to$ 136.54 $\to$ 120.06）。
此一使能效應正是 \S\ref{sec:codesign} 協同必要性論點的直接實驗驗證。

\section{$\theta$ 參數敏感性}
\label{sec:eval-theta}
%-------------------------------------------------------------

早停的鬆緊由門檻 $\theta$ 控制。$\theta$ 越小越積極、省下的 hop 越多，但假陽性終止造成的召回率損失也越大。
我們在固定資料集與快取配置下掃描 $\theta$，觀察其對召回率與 QPS 的取捨，並確認最優區間的穩定性。

曲線在 $\theta \in [1.0, 1.2]$ 呈現清楚的單調取捨：$\theta$ 越小、早停越積極，QPS 越高但 recall 損失也越大
（$\theta=1.0$ 時 recall 掉到 $0.897$，明顯過於激進）。但 $\theta \ge 1.3$ 之後 recall 已趨近飽和（$0.980$--$0.981$，
與無早停的 baseline recall $0.9809$ 幾乎相同），此區間內 QPS 的微幅波動（例如 $\theta=1.3$ 比 $\theta=1.4$ 低）
更可能是 server-mode 量測雜訊而非真實趨勢——$\theta=1.3$ 這個點的 P99/P999 出現異常尖峰（$27.0$/$32.4$\,ms，
遠高於相鄰的 $\theta=1.2$ 與 $1.4$），支持雜訊解釋。以平均 I/O 而非 QPS 判斷則單調性完全成立（$39.78 \to 163.88$
隨 $\theta$ 遞增而遞增），因此本研究以平均 I/O 作為判斷早停積極程度的主要依據。
本文選用的 $\theta=1.3$ 落在「recall 已飽和、I/O 尚未過度保守」的甜蜜點區間。

$\theta$ 的最優點與資料集的 PQ 量化誤差分布有關，不同維度與 segment 數的 PQ 設定下略有差異，
因此本文將 $\theta$ 視為需依資料集校準的參數，而非固定常數；本研究在 SIFT1B（十億級規模）上的驗證即發現
同一 $\theta$ 值（沿用自 SIFT100M 的 $1.4$）明顯過於保守，需重新掃描後校準為 $\theta=1.25$ 才能取得有意義的 I/O 節省，
說明 $\theta$ 不只跨資料集需要校準，跨資料規模也是如此。
