% ─── 章節破題 ───────────────────────────────────────────────
第~\ref{ch:motivation}~章的分析揭示了兩個獨立但相互影響的問題：
其一，beam search 中大多數 hop 是可消除的無效工作（O1、O2）；
其二，收斂偵測的可靠性依賴於搜尋初期的 top-$k$ 覆蓋品質（O3）。
這兩個問題共同決定了 PaceANN 的設計空間：
\textbf{只改動 ET 不改動快取，終止信號不可靠；
只改動快取不改動 ET，I/O 節省有上限。}
兩者必須協同設計，才能構成一個自洽的系統。

PaceANN 的整體架構如圖~\ref{fig:overview} 所示：在原本的 DiskANN 搜尋路徑上，
每個 hop 先由收斂感知早停（ET）判斷是否可停，再查詢並發感知動態快取（BNC）；
命中則直接由 DRAM 取得鄰居與全精度向量，未命中才回到共享的 SSD I/O 佇列。
兩個機制的共同目標，是減少進入該佇列的冗餘讀取。

%-------------------------------------------------------------
\section{快取節點選擇的拓撲基礎}
\label{sec:topology}
%-------------------------------------------------------------

在有限的 DRAM 預算下，要決定優先快取哪些節點的鄰居列表，關鍵在於估計各節點被存取的頻率。
DiskANN 的 beam search 每次都從固定的入口節點（medoid $m^*$）出發，沿 Vamana 圖的有向邊逐步逼近 query，
因此一個節點被造訪的機率，和它在圖上離 medoid 的遠近高度相關。
離 medoid 越近的節點越常被造訪：medoid 的直接鄰居幾乎每次查詢都會在第一個 hop 被納入候選，
而距離越遠的節點，能經過它的查詢路徑越少，被造訪的機率也隨之快速下降。
這個傾向只由圖的拓撲決定、與查詢分布無關，所以在索引載入後、還沒有任何查詢歷史時就能估算出來。

據此，冷啟動時較合理的預填策略是從 medoid 出發做廣度優先走訪（BFS），按層序把最靠近入口的節點填入快取，
相當於依預期造訪頻率由高到低選取，能立即保護最熱的入口鄰域。
若改用隨機採樣，大量離入口較遠、頻率偏低的節點會佔掉預算，命中率因此偏低，
這也是 Starling 以隨機採樣建立 navigation graph 時命中率不高的原因之一。
對含多個 medoid 的索引，我們把種子預算平均分給每個 medoid 各自 BFS，
避免某些入口鄰域在冷啟動時完全沒有覆蓋。

不過，入口鄰域雖然最熱，光靠這種靜態覆蓋並不足以支撐整體效能。
每個查詢真正花時間的是它自己的收斂區，也就是 beam search 逼近答案時、在答案附近才展開的那些節點。
這些節點因查詢而異，還會隨查詢分布（例如 RAG 中熱門主題的變動）持續漂移，
任何在啟動時就固定下來的集合都蓋不到（第~\ref{ch:motivation}~章的 O3）。
BFS 種子蓋得住入口熱區，卻蓋不住各查詢的收斂熱區。
這也是 PaceANN 不採用永久靜態快取，而改用會在查詢期間依實際存取分布持續演化的動態快取（§\ref{sec:cache}）的原因；
BFS 種子在這裡只是冷啟動的起點。

%-------------------------------------------------------------
\section{並發感知動態快取（BNC）}
\label{sec:cache}
%-------------------------------------------------------------

如 §\ref{sec:topology} 所述，靜態覆蓋只能保護入口熱區，
無法涵蓋各查詢專屬、且隨分布漂移的收斂熱區。
因此 PaceANN 的快取以需求驅動的動態快取為主體（BoundedNeighborCache，BNC），在固定記憶體預算內於查詢期間持續演化，
自動反映實際工作負載的存取模式；系統啟動時以 §\ref{sec:topology} 的 BFS-from-medoid 種子預填，消弭冷啟動初期的空窗，
其後就交由 BNC 的替換策略託管，平滑演化到當前 workload 的分布。

BNC 的設計同時受四個約束牽制。查找必須支援高並發：16 個 worker thread 會同時讀取，若用全域鎖會造成嚴重的序列化瓶頸。
插入的頻率相對低：每個節點在首次從 SSD 讀回時插入一次，之後只有被驅逐才需再插入，因此插入路徑可以承擔較高的成本。
記憶體必須有固定上限，不能因工作負載波動而超出預算。淘汰只需要近似 LRU 的語義，不必付出精確 LRU 維護 doubly-linked list 的代價。

為滿足這些約束，BNC 把節點分到 $S$ 個 shard，每個 shard 各自維護一個 CLOCK 替換環與一把 \texttt{shared\_mutex}。
shard 數不是固定常數，而是由 worker thread 數 $T$ 推導：取 $S = 2^{\lceil \log_2 T \rceil}$（$T$ 向上取到 2 的次方），
讓 lock stripe 的數量對齊真正的並發寫入者數量。取 2 的次方的用意在於 shard 選擇可用位元遮罩 \texttt{node\_id \& (S$-$1)} 完成，
比取模更省；本研究 $T = 16$，故 $S = 16$。
高頻的查找走 \texttt{shared\_lock}（允許多個並發讀者，讀彼此不互斥），做一次雜湊表查找並遞增 atomic reference 計數（飽和上限 4），約 10--20\,ns。
低頻的插入與驅逐則走 \texttt{unique\_lock}，且以 \emph{non-blocking} 的 \texttt{try\_lock} 進行：搶不到鎖時直接略過該次插入，而不阻塞查找路徑——
被略過的節點下次仍會遇到、再擇機補入，因此高並發下查找延遲不受插入競爭影響。掃描 CLOCK hand 時，對 reference 計數大於 0 的 slot 遞減一次（second chance），第一個計數為 0 的 slot 即原地替換。
正因為寫入是非阻塞的，shard 數不需要額外的競爭餘裕倍率；實測將 $S$ 由 16 放大到 256，吞吐量的變化在量測雜訊範圍內，顯示效能對 $S$ 並不敏感。
相較於精確 LRU，CLOCK\cite{corbato1968clock} 省去了每次查找都要更新 doubly-linked list 的 exclusive lock，在讀遠多於寫的 server 場景下，吞吐量與尾延遲都優於精確 LRU 及其自適應變體（如 ARC\cite{megiddo2003arc}）；
近期雖有以學習式策略提升命中率的淘汰法\cite{zhou2025threelcache}，但其決策開銷不適合置於本系統的高並發查找熱路徑。

除了替換策略，BNC 還做了座標共存（coordinate co-storage）。標準 DiskANN 的搜尋流程分為兩個階段：
（1）traversal：以 PQ 距離引導的 beam search，只需鄰居 IDs；
（2）re-rank：取 top-$k$ 候選的完整原始向量，計算精確距離。
Re-rank 階段需要從 SSD 讀取 $K$ 個節點的完整向量，
即使 traversal 已全部命中快取，也仍有不可避免的 SSD 存取。

BNC 在快取項目裡一併存下節點的原始座標（raw uint8 coordinates），
命中 BNC 的節點在 re-rank 時就能直接從 DRAM 取得精確向量，完全省掉 re-rank 的 SSD 讀取：

\begin{center}
\texttt{struct Entry \{ uint32\_t* neighbors;\ uint8\_t* coords;\ bool ref; \}}
\end{center}

此設計使得「BNC 命中的節點貢獻零 SSD I/O」在整個搜尋流程中成立，
而非僅在 traversal 階段成立。
代價是每個 BNC entry 需要額外儲存 $d_\text{raw}$ bytes 的座標（例如 128 bytes for uint8 SIFT），
在記憶體預算配置時需一併納入計算。
BNC 的整體結構與查詢／插入路徑如圖~\ref{fig:bnc} 所示。

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.95\textwidth]{img/bnc_cache.png}
  \caption{並發感知動態快取（BNC）。節點依 \texttt{node\_id \& (S$-$1)} 分到某個 shard，
  每個 slot 以座標共存的方式同時保存鄰居列表與全精度向量。
  命中時直接由 DRAM 供應這兩者（導航與 re-rank 皆免回盤）；
  未命中才發出 SSD 讀取，讀回後連同鄰居與座標一併插入，並更新 CLOCK 計數。
  查找走 shared-lock（允許並發讀者），插入以 non-blocking 的 try-lock 進行，搶不到即略過。}
  \label{fig:bnc}
\end{figure}

除了啟動時的 BFS 種子外，BNC 採用需求驅動（demand-fill）的填充方式：
節點的鄰居列表在首次從 SSD 讀取後才被填入，而不是批量預載。
如此 BNC 自動反映實際工作負載的存取模式，並隨查詢分布的變化持續適應。
冷啟動初期的入口空窗由 BFS 種子（§\ref{sec:topology}）填補，
其餘的收斂熱區則在服務過程中透過 demand-fill 逐步累積、由 CLOCK 替換策略託管；
因此系統\emph{不依賴}預先的代表性查詢暖機，即可在真實流量下平滑收斂至穩態命中率。

\section{PQ 引導的自適應早停}
\label{sec:et}
%-------------------------------------------------------------

早停的核心邏輯在 §\ref{sec:mot-insight} 已引入；
本節給出正式定義，並說明關鍵設計參數的含義。

具體來說，在 beam search 每次展開前，我們取 retset 中 PQ 下界最小的未展開候選 $v_\text{best\text{-}unexp}$，
把它的 PQ 下界 $d_\text{PQ}(q, v_\text{best\text{-}unexp})$，和用已讀回全精度向量算出的第 $2k$ 名候選精確距離 $d_\text{exact}(q, v_{2k})$ 相比：

\begin{equation}
  d_\text{PQ}(q,\, v_\text{best\text{-}unexp}) \;>\; \theta \cdot d_\text{exact}(q,\, v_{2k})
  \label{eq:et-gate}
\end{equation}

一旦成立，代表 frontier 中最有希望候選的樂觀下界都已經劣於現有第 $2k$ 名的實際距離，再展開下去幾乎不可能改變 top-$k$，於是終止並返回。
這裡刻意用跨尺度的比較：待展開端用便宜的 PQ 下界、已收斂端用精確距離，並以第 $2k$ 名（而非第 $k$ 名）當門檻，替 recall 多留一點保守邊界。
$d_\text{exact}$ 用的是 traversal 過程中已經讀回的全精度向量（包含 BNC co-storage 命中的節點），所以整個判斷不會額外觸發任何 SSD 讀取。

門檻 $\theta$ 控制停止的保守程度。$\theta=1$ 時只要最佳候選的下界等於收斂端邊界就停，完全信任 PQ 近似、最為激進；$\theta\to\infty$ 則永不停止，等同原始 DiskANN；
實務上取 $\theta$ 約 $1.1$ 到 $1.3$，替 PQ 量化誤差留一點容忍帶，在保守與省 hop 之間取得平衡。
$\theta$ 的最優值和資料集的 PQ 壓縮誤差分布有關，不同維度與 segment 數的 PQ 設定下略有差異，其敏感性分析放在第~\ref{ch:method}~章。

為了避免誤判，我們在停止條件上再加兩道安全網。單一 hop 的 PQ 下界可能因量化噪聲短暫越過門檻，
而搜尋最初期候選還少、$d_\text{exact}(q, v_{2k})$ 也不穩定，這些都可能造成假陽性終止。
第一道是 patience 計數：式~\eqref{eq:et-gate} 必須連續在 $P$ 個 hop 都成立才真正終止（典型 $P \approx 6$），藉此濾掉單跳噪聲的偽觸發。
第二道是最小 hop 數 $t_\text{min}$：前 $t_\text{min}$ 個 hop 內一律不允許早停，確保 top-$k$ 累積到夠穩定後才開始判斷。
這兩道防護都不依賴任何靜態快取層；收斂端的精確距離來自 traversal 已讀回、並由動態快取的 co-storage 保存的全精度向量。

\section{快取與早停的協同必要性}
\label{sec:codesign}
%-------------------------------------------------------------

本節論證快取與 ET 的協同不是「兩個獨立優化的疊加」，
而是一個設計中的相互依賴關係：
兩者缺少任何一個，另一個都會出現功能性的退化。

先看只有快取、沒有早停的情況。若只部署動態快取，beam search 仍按固定 $L$ 跑完整段 hop 序列；
命中快取的 hop 雖然把 SSD 讀取換成約 10\,ns 的 DRAM 存取、大幅降低 traversal 成本，但 hop 的數量本身並沒有減少。
如 §\ref{sec:mot-diminishing} 所述，$L=150$ 時約有七成的 hop 在收斂後才執行；有了快取，這些無效 hop 仍會消耗 DRAM 頻寬、shard 鎖與 CPU 的 PQ 計算。
在高並發下，這些原本被 SSD I/O 掩蓋的競爭，反而會在快取命中率提高後浮現成新的瓶頸。

反過來，只有早停、沒有快取也不行。少了快取保護前期 hop，搜尋剛起步時 top-$k$ 覆蓋不足，
用來比較的收斂端距離不穩定，早停就容易假陽性，逼得 $\theta$ 必須設得很保守。
在無快取的冷啟動下，即使 $\theta=1.2$ 也可能讓 recall 損失超出可接受範圍，只好把 $\theta$ 調到 1.4 以上；
但這樣一來早停幾乎不觸發，省下的 hop 有限，相較 baseline 幾乎沒有改善。

兩者一起用時就互補了：

\begin{enumerate}
  \item 動態快取（含 BFS 種子與 demand-fill 累積的熱點）使前期 top-$k$ 以 DRAM 速度快速填充，
    並透過 co-storage 直接提供收斂端所需的\emph{精確}距離 $d_\text{exact}$。
  \item top-$k$ 穩定後（通常在 hop 5\textasciitilde 6），$d_\text{exact}(q, v_{2k})$ 可靠，
    ET 的跨尺度門檻得以在較小的 $\theta$ 下穩定觸發。
  \item ET 在收斂點停止，消除後續的無效 hop——
    這些 hop 即使在快取命中的情況下也是純粹的 DRAM 與 CPU 浪費。
  \item 快取在收斂區持續命中，使 ET 之前的有效 hop 更快完成，進一步縮短整體延遲。
\end{enumerate}

在此協同下，一個 query 的服務路徑可形式化為：

\begin{equation}
  \text{Latency} = \underbrace{h^* \cdot c_\text{DRAM}}_{\text{有效 hop（動態快取）}}
                 + \underbrace{0}_{\text{無效 hop（ET 阻止）}}
                 + \underbrace{K \cdot c_\text{SSD\_rerank}}_{\text{re-rank（有 coord-co-storage 時 = 0）}}
  \label{eq:latency-model}
\end{equation}

其中 $h^*$ 是 oracle 停止 hop，$c_\text{DRAM}$ 是每次快取命中的成本。
這個模型代表系統在理想條件下的延遲下界，
實際延遲高於此下界的原因主要是 BNC 命中率不為 100\%（仍有部分 SSD 讀取），
以及 shard 鎖競爭的開銷。

\section{Server 模式並發架構}
\label{sec:server}
%-------------------------------------------------------------

PaceANN server 採用固定執行緒池：$T$ 個 worker thread 各自持有一個 TCP socket 監聽，
並各有一份 thread-local 的暫存空間（存放 retset、visited bitmap 等 per-query 狀態），避免跨查詢的狀態污染。
連線被接受後，由空閒的 worker 跑完整段搜尋流程再關閉連線，不需要跨 thread 的工作竊取或 continuation。

BNC 的 shard 鎖在高並發下的競爭程度，取決於同時執行中的查詢數量。為此 server 維護一個原子計數器 \texttt{\_active\_searches}，
在進入 \texttt{cached\_beam\_search} 時遞增、返回時遞減，作為動態 I/O 並發控制的負載信號。

利用這個信號，PaceANN 提供一個 I/O 並發控制選項。在高並發時（$C \gg T$，連線排隊），
所有 $T$ 個 thread 同時執行 beam search，
每個 hop 最多提交 $W$ 個 SSD 讀取，
使 $D_\text{eff}$ 在快取未命中時可達 $T \times W$。
為控制 NVMe 佇列深度，
系統提供 \texttt{--io\_concurrency N} 選項：

\begin{equation}
  W_\text{eff} = \min\!\left(W,\; \max\!\left(1,\; \left\lfloor \frac{N}{A} \right\rfloor\right)\right)
  \label{eq:io-concurrency}
\end{equation}

其中 $A = \texttt{\_active\_searches}$，
$N$ 為目標最大並發 SSD 讀取數。
當 $A = T = 16$、$N = 64$ 時，$W_\text{eff} = 4$，
每 hop 的 SSD 請求數下降 50\%，
以小幅 recall 代價換取 NVMe 佇列的穩定。
在 BNC 充分暖機的情況下，$W_\text{eff}$ 的縮減對實際 SSD 請求量的影響較小
（因多數 hop 命中快取，frontier 中真正需要 SSD 的節點本就不多），
主要作用是作為快取冷啟動期間的保護機制。

通訊層採用簡單的二進位 TCP 協定：client 送出固定格式的請求封包（查詢向量、$K$、$L$、$\theta$ 與 hop\_budget），
server 回傳 top-$K$ 的 node ID 與精確距離。所有計時（平均、P50、P99、P999）都在 server 端從收到完整請求後才開始計算，
不含 TCP 建連與傳輸時間，讓延遲量測只反映搜尋本身的計算成本。

\section{設計摘要}
\label{sec:design-summary}
